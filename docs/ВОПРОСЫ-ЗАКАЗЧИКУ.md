# Спорные / нелогичные места — вопросы заказчику

Ниже — места, где текущее поведение системы допускает разные толкования.
Часть проблем уже исправлена (см. конец файла), остальные требуют решения заказчика,
потому что «правильный» вариант зависит от бизнес-процесса цеха.

## Требуют решения заказчика

### 1. Двойной учёт оплат (важно!)
Оплата, отмеченная в графике платежей договора («Платёж поступил»), теперь **автоматически**
создаёт поступление в кассе (модуль «Финансы»). Но бухгалтер по-прежнему может внести то же
поступление вручную — тогда сумма задвоится.
**Вопрос:** договорные деньги вводим только через график платежей, а ручные операции — только
для внедоговорных доходов/расходов? Если да — стоит заблокировать ручной ввод поступлений с привязкой к договору.

### 2. Закрытие договора ничем не обусловлено
Договор можно перевести в «Закрыт» без полной оплаты и без отгрузки продукции.
**Вопрос:** блокировать ли закрытие, пока оплачено < 100% и/или не отгружен весь объём?

### 3. Метод расчёта себестоимости материалов
Средневзвешенная цена материала считается **по всем партиям за всю историю**, а не по текущему
остатку. Если цены выросли, себестоимость занижается.
**Вопрос:** какой метод нужен — FIFO, по последней закупочной цене или средняя по остатку?

### 4а. Сторно прихода (реализовано)
У партии прихода есть кнопка **«Сторно»** — она корректно откатывает и остаток, и
среднюю цену к состоянию до прихода (добавляет компенсирующее движение «возврат» и убирает
партию). Если материал уже израсходован — сторно блокируется. Полноценного «возврата
поставщику» с оформлением документа пока нет — уточнить, нужен ли.

### 4. Списание материалов не привязано к партиям
Партионный учёт ведётся только на приход; списание в производство идёт общей суммой со склада.
Отчёт «сколько осталось в каждой партии» невозможен.
**Вопрос:** нужно ли партионное списание (FIFO по партиям)? Это заметная доработка.

### 5. Последовательность этапов производства не блокируется
Можно начать «Отделку» раньше «Кроя» — система это позволяет (этапы независимы).
**Вопрос:** запрещать ли запуск этапа, пока предыдущий не завершён? Иногда цеха работают параллельно, поэтому не стали блокировать без согласования.

### 6. Кнопки и права: роль «только просмотр»
Права проверяются на сервере (запись запрещена — вернётся ошибка 403), но в интерфейсе кнопки
видны всем.
**Вопрос:** скрывать ли элементы управления в зависимости от роли? (чисто интерфейсная доработка)

### 7. Авто-заявка поставщику
Заявка создаётся в статусе «Черновик» и её можно сразу «Принять», минуя статус «Отправлена».
Реальной отправки поставщику (email/мессенджер) нет.
**Вопрос:** нужна ли автоматическая отправка на email поставщика и обязательный шаг «Отправлена»?

### 8. Коэффициенты прогноза (воронка)
Ожидаемые поступления считаются с фиксированными вероятностями: новый — 10%,
согласование — 40%, в работе — 90%.
**Вопрос:** согласовать коэффициенты или сделать их настраиваемыми.

### 9. Уведомления общие, а не персональные
Уведомления видят все пользователи, и «прочитано» одним пользователем скрывает его у всех.
**Вопрос:** нужны ли персональные уведомления (например, менеджеру — только его договоры)?

### 10. Excel-импорт перезаписывает договоры
Импорт находит договор по номеру и **обновляет** его, минуя цепочку статусов (можно импортом
«перепрыгнуть» из «Новый» в «Закрыт»).
**Вопрос:** ограничить импорт только созданием новых договоров?

### 11. Прайс-листы не подключены к интерфейсу
В базе есть прайс-листы «разным клиентам — разные цены» (и API для них), но при создании
договора цена вводится вручную, прайс нигде не подставляется.
**Вопрос:** подставлять ли цену из прайса клиента при создании договора / позиций?

### 12. QR-код генерируется, но не сканируется
QR по SKU есть на карточке изделия, однако сценария сканирования (приёмка/отгрузка со сканером)
в системе нет.
**Вопрос:** нужен ли рабочий процесс со сканером (например, отгрузка сканированием)?

### 13. «Чистая прибыль (оценка)» в аналитике
Считается как маржа × продано — это **оценка по нормативной себестоимости**, а не факт по ОПиУ.
Реальная прибыль — в модуле «Финансы». Стоит проговорить с заказчиком, чтобы не путать эти цифры.

### 14. Удаление производственного заказа не откатывает списание — ЧАСТИЧНО ИСПРАВЛЕНО
Раньше удаление запущенного ПЗ не возвращало материалы. Теперь **удалять можно только
запланированный ПЗ** (до списания); запущенный/завершённый удалить нельзя.
**Остаётся вопрос:** нужна ли отдельная операция «Отменить с возвратом материалов на склад»
для запущенных заказов?

## Технические замечания
- Для AI-ассистента нужен `ANTHROPIC_API_KEY` в переменных окружения сервера — без него чат вернёт понятную ошибку.
- Пароли демо-пользователей (`admin12345`) обязательно сменить перед продакшеном.
- SQLite подходит только для демо; для продакшена — PostgreSQL (см. README).

## Уже исправлено (23.07.2026)
1. **Вход под админской учёткой не работал** — в базе вообще не было пользователя `admin`:
   команда `seed_demo` (создаёт демо-данные и учётки) ни разу не запускалась. Выполнена;
   также учётке `abylai` выдана роль администратора. В README добавлено предупреждение.
2. **Дублирование уведомлений** — прочитанное уведомление создавалось заново при каждом
   обновлении страницы. Исправлено.
3. **Запуск ПЗ без материалов** — материалы списывались «в минус» без предупреждения.
   Теперь запуск блокируется с перечнем недостающих материалов.
4. **Завершение ПЗ при невыполненных этапах** — можно было сдать заказ на склад, не завершив
   крой/пошив/ОТК. Теперь система требует завершить все этапы.
5. **Оплата не попадала в финансы** — «Платёж поступил» в договоре не отражался в Cash Flow.
   Теперь создаётся денежная операция автоматически (см. вопрос №1).
6. **Отгрузки не существовало в интерфейсе** — рейтинг «Продано» в аналитике всегда был пустым,
   готовая продукция копилась бесконечно. Добавлена форма «Отгрузка клиенту» на складе.
7. **Интерфейс переведён на русский полностью** (frontend, статусы, этапы, уведомления, README).
